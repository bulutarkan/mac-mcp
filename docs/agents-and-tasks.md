# Agents and Scheduled Tasks

Delegating work to Codex, Claude Code and OpenCode agents (and Kimi Code, Grok Build, Antigravity, pi, Cline, Kilo Code and Goose): resume, worktrees, admission, notifications, budgets, memory, skills, role learning and Scheduled Tasks.

## Durable delegated-workflow resume

Delegated agents now get a provider-independent durable workflow checkpoint under `~/.mac-mcp/workflows/`. The checkpoint stores the original task **input hash**, provider/session lineage, resume generation, a sanitized provider milestone cursor, and a bounded chain of verified Mac MCP side-effect receipts. Receipt rows contain tool/family metadata plus hashes of arguments/results; raw prompts, commands, file contents, typed values, credentials, and tool payloads are not copied into the checkpoint store. Workflow and agent-map files are owner-only (`0600`) inside an owner-only directory (`0700`) and carry an integrity hash so corrupt or mismatched state fails closed.

A normal `agent_action(action="retry")` is only allowed while replaying the original prompt is still safe. Once a verified side effect has happened, a resume generation already exists, or the outcome becomes uncertain, fresh replay returns `409 retry_replay_unsafe`. For an interrupted agent with a verified checkpoint, `agent_action(action="resume")` continues the **same provider session** with an incremented generation and a compact receipt summary that explicitly instructs the provider not to repeat completed side effects. If the provider session cannot be recovered, the input hash/session does not match, the checkpoint is corrupt, or direct provider-native mutation made the commit state unverifiable, Mac MCP returns an outcome-unknown conflict rather than guessing.

Mac MCP can issue strong receipts only for side effects routed through its own tool boundary. Before a mutating Mac MCP tool executes, it durably writes a hashed **pending side-effect intent**; only a successfully returned result can convert that intent into a verified receipt. If the process dies in between, the pending intent survives and the workflow becomes outcome-unknown instead of replayable. Direct Codex/OpenCode/Claude Code shell or file mutations are therefore treated conservatively across a crash boundary. This is intentional: durable resume prefers refusing an ambiguous replay over claiming a destructive action is safe to repeat. Agent/dashboard metadata exposes `workflow_id`, `resume_generation`, checkpoint state/safety, pending/verified side-effect counts, the sanitized cursor, last durable checkpoint time, and whether an interrupted agent is safely resumable.

Client cancellation follows the same safety model. Sync MCP tool bodies receive a shared cooperative cancellation context even when they run in a worker thread. Mac MCP terminates process groups it owns, stops jobs created by a cancelled parallel-command call, interrupts browser/native polling, releases browser tab leases through normal context cleanup, and runs bounded native focus restoration before propagating cancellation. Telemetry records `cancelled` separately from ordinary failures. If a mutating operation is opaque or cannot be proven stopped before its effect, its durable intent is closed as `client_cancelled_outcome_unknown`, telemetry/steering expose `outcome_unknown`, and automatic retry/resume is blocked rather than risking a duplicate side effect.

## Isolated Git worktrees for write agents

Delegated agents with `access_mode="workspace_write"` use `git_isolation="auto"` by default. When `cwd` is inside a Git repository and the write scope can be safely attenuated, Mac MCP creates an ephemeral branch/worktree under an already-authorized workspace root, remaps the child cwd/path scope to that checkout, and records the base commit plus changed-file/diff metadata. `git_isolation="required"` fails closed when that guarantee cannot be enforced; `off` keeps the original checkout. Read-only agents do not need a worktree, while unrestricted `full` access is never presented as worktree-confined. Non-Git workspaces gracefully keep the existing behavior in `auto` mode.

Parallel sibling tasks receive separate worktrees. A team pins one Git base commit, downstream DAG/reviewer tasks fan in completed dependency patches into a fresh isolated checkout, and bounded coder revisions/resumes continue the same worktree rather than losing in-progress edits. Cancel/crash leaves the isolated checkout recoverable. `get_agent`/`wait_agents` expose the worktree path, base, changed files, diff stat and apply state.

Returning changes to the user's source checkout is explicit: `agent_action(action="apply")` is **local/root control-plane only**. It refuses touched paths that are dirty, detects touched-path changes since the agent base, preflights the patch against the current HEAD in a temporary integration worktree, rechecks per-path fingerprints immediately before mutation, and rolls back already-copied preimages if an internal apply step fails. It never runs `git reset --hard`, `git clean`, or an automatic source-tree cherry-pick/merge. Unrelated user changes are left alone. Conflicts return the affected paths and no intentional source-tree mutation. `despawn` refuses unapplied isolated changes until they are either safely applied or explicitly discarded; shared resume/revision worktrees stay alive until their last agent reference is gone.

## Global cross-team agent admission

Independent delegated teams share one persisted admission queue before provider processes start. The scheduler applies a global active-agent ceiling plus provider-specific ceilings across teams, so several teams cannot each consume their own `max_parallel` budget and collectively overload the same provider. Defaults are 8 global and 8 per provider; operators can tune `MAC_MCP_AGENT_GLOBAL_ACTIVE_LIMIT`, `MAC_MCP_AGENT_PROVIDER_LIMIT`, and provider overrides such as `MAC_MCP_AGENT_PROVIDER_LIMIT_OPENCODE`, `_CODEX`, or `_CHATGPT`. Admission leases are owner-only local state, heartbeated by running workers, and reclaimed after `MAC_MCP_AGENT_ADMISSION_TTL_S` if a worker disappears. `MAC_MCP_AGENT_ADMISSION_QUEUE_LIMIT` bounds persisted waiting work.

The queue is FIFO-aware without turning an unrelated blocked resource into a global head-of-line stall. Older runnable work keeps priority for scarce provider/global slots and conflicting resources, while a task blocked on workspace A does not prevent a younger task from using independent workspace B. Task/team state exposes `queued`, queue position/reason/details, resource claims, and global/provider active counts. The Operations dashboard shows the live global active/limit and queued count. Team cancel removes its queued requests immediately; active leases remain held until their provider/worker is actually stopped. Normal completion wakes other queued teams automatically, and expired crash leases are pruned fail-safe on the next admission/snapshot. Existing ChatGPT throttle state feeds the same admission decision: active cooldown prevents new admission, and the post-throttle reduced-concurrency window temporarily lowers ChatGPT's effective global scheduler provider limit to one while the existing start-spacing gate controls the exact safe launch time.

`spawn_agents` tasks may optionally declare `resources=[...]` claims. Supported kinds are `workspace`, `path`, `file`, `browser_tab`, `native_app`, `native_window`, `process`, and `clipboard`; modes are `read` or `write`. Read/read claims may coexist, while any overlapping write is serialized. Path/file/workspace IDs are resolved inside the task's delegated path scope, browser-tab claims must fit the task browser scope, and existing browser action-time tab leases remain the final ownership guard rather than being replaced. Read-only path scopes are auto-claimed as shared reads. Non-Git workspace writes are auto-claimed as exclusive writes; #50 isolated Git worktrees intentionally avoid a coarse source-repository write claim so independent sibling worktrees can still run concurrently.

`read_file` also returns an additive `revision` using the same fingerprint as filesystem transaction conflict checks. A task may attach that value as `expected_revision` on a `kind="file"` claim. Mac MCP rechecks it **before admission/provider start**; a mismatch returns `file_revision_conflict` and the provider never begins, providing a CAS-style guard for file mutation races.

## Native agent completion notifications

The macOS menu app can optionally notify you when delegated work finishes while Mac MCP is in the background. The feature is **off by default** and macOS notification permission is requested only when you explicitly enable **Agent Notifications** in General Settings.

Standalone agents generate one terminal notification for completion or needs-attention states. Multi-agent teams are coalesced into one team-level terminal notification instead of one notification per child. Notification content is intentionally minimal: only a sanitized agent/team label is shown, never raw prompts, results, URLs, file paths, or secrets. Clicking an alert opens the local authenticated Operations dashboard focused on the relevant agent or team. Delivery timing, Do Not Disturb, Focus modes, and presentation remain under macOS control.

## Scheduled Tasks

**Settings › Scheduled Tasks** runs work on its own at a set time or on a recurrence: once, daily, weekly (chosen days), monthly (a day of the month; 29–31 fall back to the month's last day), every few hours, or a 5-field cron expression under Advanced. Times are this Mac's local time and stay on the wall clock across daylight-saving changes.

- **AI task**: a prompt that a delegated agent (Codex, Claude Code or OpenCode, whichever is on) runs in a chosen folder. The run keeps the agent's summary, full report and the files it named.
- **Recipe task** (#257): a saved recipe (see Recipes) replayed with values you give, at a set time or when a file arrives, with no model call. Values are checked against the recipe's parameters when the task is saved; a value may hold `{file}` (folder tasks) or a date word such as `{today}`, filled in at each run. The recipe runs through the same path as the `recipe` tool (permission profile, scope, verification and its run timeline); a recipe that is a draft, paused or deleted makes the run fail with that reason, and the task card says so.
- **Script task**: a file run with the program its type implies (`.sh/.zsh/.bash`, `.py` with a nearby `.venv` when there is one, `.js/.mjs`, `.applescript/.scpt`, `.rb`, `.pl`, or any executable), or a command line. Arguments, the program, the folder and a time limit are under Advanced. Scripts get a plain login environment, not Mac MCP's keys. The run keeps the exit status and the end of the output.

Runs happen inside the Mac MCP server, which sleeps until the next due run (waking at most once a minute while tasks are active, never when none are). A run whose time passed while the Mac slept or Mac MCP was stopped is not run late: it is recorded as **Skipped** with the reason, and **Run now** runs it on demand. A task with **Run it once when the Mac is back** turned on (`"missed": "run_once"`, timed tasks only) instead runs once as soon as the Mac is back, for the latest missed time, marked **Catch-up** in its history; earlier missed times are recorded as one skipped entry that the catch-up run covers, so a long sleep starts at most one run, and when a run is due right then that run covers them and no catch-up is added. One run per task at a time; each task keeps its last 50 runs for at most 90 days in `~/.mac-mcp/state/scheduled_tasks.sqlite3` (owner-only). Paused observation skips AI runs; private mode keeps only how a run ended.

A run record has two layers. Its **skeleton** (how it ended and why, when, the exit code, usage, the checks, and per step only its kind, status and a fingerprint) lives as long as the run. Its **contents** (the result, the output, and each step's text, inputs and output) are masked for known secrets such as tokens and `NAME=value` keys when written, and removed after **Settings › Privacy › Scheduled task run details** (7, 30 or 90 days; 30 by default, `privacy.run_detail_retention_days`), checked whenever runs are read, when the scheduler wakes and when the period changes; the report then says so, and nothing is read back from the agent's files. Each step with inputs or a command gets a fingerprint, `v1:` and an HMAC-SHA256 over a canonical JSON form under a key kept on this Mac (`state/run-fingerprint.key`, owner-only; like the rest of `~/.mac-mcp` it is readable by anything that runs as you, an agent with shell access included, and goes into backups unless Mac MCP data is kept out of Time Machine), and the run gets one over its steps (`steps_fp`). Two runs that did the same thing have equal fingerprints even after their contents are gone, while a guessable value (a common path, a short command) cannot be confirmed from what is stored. A fingerprint says that inputs were equal, not that the run was right; masking catches known secret shapes, not every name or personal detail, which is why the contents expire.

**Check the result** (under Advanced) separates "it ran" from "it made what it should": name a file the run should leave (up to five through the API, `verify` / the tool's `expected_files`, each with a smallest size and whether this run must have written it; a relative path is inside the task's folder). After a run that finished, Mac MCP checks each file by its size and time only: it never opens it, and a check fails when the file itself is a link or a folder (links among the folders above it are followed). A relative path is fixed to the task's folder when the task is saved. The run stays **Done** and is marked **Checked**, or **Check failed** with the reason (for example "report.csv is missing"), also in the notification. A failed, skipped or timed-out run is never checked, so a check never turns a failure into a success, and nothing is ever run again on its own. A file's time shows only that something wrote it during the run, not that its contents are right. In private mode only whether the checks passed is kept.

A check can also look outside this Mac (#228), for a run that says it is done while the sheet row or the posted reply is not there. A **URL** check (`{"url": "https://...", "status": 200, "contains": "..."}`; in the editor, type an address instead of a file) fetches the page with a plain GET and no headers, so no credentials leave this Mac, and expects the status and, optionally, a piece of text. A **tool** check (`{"tool": "sheets__read_range", "arguments": {...}, "contains": "..."}`; in the editor, type the tool's `server__tool` name, then its arguments as JSON) calls one of your own MCP servers' tools, only when both the server's annotation and Mac MCP's risk entry say it is read-only; a tool that may change anything is never called. `{today}` and the other date words work in the URL, the text and the arguments. Text that appears late is looked for again after 5 and 10 seconds; nothing is ever written or sent again. A check that could not look (unreachable, server not connected, timeout) is **Couldn't check**, not a pass and not a plain failure, also in the notification. Page and tool contents are never stored, and a URL is kept without its query.

**Runs that never started** (#225): the app asks Mac MCP once a minute whether a run is more than 5 minutes past its time without having started, outside the scheduler's own loop, and posts "<task> didn't start" once per run; the task's card says "Didn't start at 09:00" in orange. Right after the Mac wakes, or after Mac MCP answers again, the scheduler gets those 5 minutes to record what it slept through first. When Mac MCP stops answering while it should be running (not after you stopped it), a run that came due since its last answer gets "<task> may not have run". Tasks that run when a file arrives have no time to miss and are not watched this way.

**A run stopped at its time limit keeps what it did** (#226): the agent gets up to 10 seconds to stop, and its steps and usage so far are kept. Every run that did not finish says what is partial: the steps, the usage (or that it is unavailable), and that outside effects are unknown. Mac MCP never resumes or retries a run on its own.

**Resume** (#226): when an AI task with a data step failed after its data step finished, the run report offers **Resume**. It starts a new run that skips the data step and gives the agent the data that step printed for the failed run, so a script that pulls or changes data is not run twice. Before it starts you are told when the data was printed and that what the agent did in the failed run is unknown, so it may do some of it again. Mac MCP resumes only when nothing is uncertain: the task has not changed since the run (compared by fingerprint), the kept copy of the data is exactly what the agent was given (data longer than 20,000 characters, or with secrets masked when it was kept, is not reused), the run's contents are still kept (not private mode, not expired), and the run was not resumed before; a run is resumed at most once, also when two resumes race. Script tasks and AI tasks without a data step have no earlier step to keep: use **Run now**. The failed run is not changed; the new one is marked **Resumed**. Only you can resume, from the app; agents have no tool for it.

**Check Again** (#226): a finished run whose checks failed or couldn't look has **Check Again** in its report. It runs the task's checks once more, read-only (a page that answered late, a sheet that was slow to update), and keeps what the first check said next to the new result. Nothing of the run is run again.

**Diagnose** (#227): the report of a failed, stopped or check-failed run has a **Diagnose** button. A read-only agent (the task's agent, or the Default Agent) reads the task's definition and the run's masked record, may look around without changing anything, and answers with the likely cause, the evidence it checked, what is unknown and the smallest fix, which it does not apply. It has 10 minutes, and at most 300,000 tokens where its agent can keep a token limit. Only you start one, from the app: agents have no tool for it, so a diagnosis never spends on its own. The run itself is not changed and nothing is retried. When the run's contents are gone (private mode, or removed after the Privacy period) no agent starts and the answer says there is not enough evidence; a diagnosis's text is removed together with the run's contents.

**When a file arrives** (When › New file) runs a task once for each new file in a folder, for example an invoice landing in Downloads. Choose the folder and, optionally, which files count (`pdf, Invoice*`: a bare word is an extension). The files already there when the task is saved don't start it. A file starts the run once it has finished copying (its size and time unchanged for 3 seconds); hidden files, folders, links and downloads still in progress (`.crdownload`, `.part`, `.download`...) are ignored. Each file runs the task once: files are remembered by name, size and time in the task database, so a restart neither repeats one nor misses one that arrived while Mac MCP was off. An AI task's agent is told which file started the run (write `{file}` in the prompt to place it yourself); a script gets it as `{file}` in its arguments or command (quoted for the shell) and as `$MAC_MCP_TRIGGER_FILE`. One run at a time per task: files that arrive meanwhile wait their turn, but files written while the task's own run is going on (or within 5 seconds after it) are taken to be its output and never start it, so a task that writes into the folder it watches does not loop. At most 30 runs an hour per task; files beyond that are recorded as **Skipped** with the reason. **Run now** runs it with the newest file there. The folder is watched with kqueue, with no polling while nothing happens and one look a minute in case an event was missed; at most 20 tasks can wait for files.

**Usage limit** (Advanced, AI tasks, off by default) stops the agent once a run reaches a number of tokens or a cost in US dollars. It works only where Mac MCP can see the usage while the agent works: tokens with Claude Code (each message), OpenCode and Kilo Code (each step) and pi (each turn); cost with OpenCode and Kilo Code, which report each step's price. Codex, Cline, Goose, Grok Build and Antigravity report usage only when they finish, and Claude Code reports its price only then, so a limit they cannot keep is refused when the task is saved, and a run whose agent can no longer keep it (the Default Agent changed) does not start and says why. With a cost limit, a step that comes without its price (some models report tokens only) stops the run as well ("didn't report a price for its work, so the $50.00 cost limit couldn't be kept"), since spending could otherwise pass the limit unseen; a model that reports a price of $0 is free and runs on. The editor names the agents that can keep each kind of limit and keeps Save off while the chosen agent (or the Default Agent) can't. The agent is stopped within a few seconds of reaching the limit; the run fails with "Stopped at its 500,000-token limit (used 512,330)", keeps what the agent did and reported before the stop, and the report shows the limit next to the usage. The time limit stays the fail-safe. An AI app can suggest a limit (`usage_limit`) like any other change, and raising or removing one is shown in the review before you approve.

**Approved scripts stay as approved** (#179): when you approve a task an AI app suggested, the review shows what its script (and data step script) contains, and the approval covers those contents: Mac MCP keeps their SHA-256 and, for text up to 100 KB, a copy. If a file changes later, the task does not run (the run fails with "job.sh changed since you approved this task") and waits for your review with the change shown as a diff; approving lets the new version run, **Not now** leaves it stopped. A file that changes while you review it is refused, so what you approve is what you saw. Tasks you create, and files you pick yourself when editing, are yours and are not bound. Only the task's own script files are covered, not files a script reads or calls.

**The agent never sees a secret the data step printed** (#179): known secret shapes in the data step's output (tokens, keys, `NAME=value` secrets, private keys) are replaced with `[REDACTED]` before the agent and its provider see it, the agent is told so, and the data step's line in the report says "secrets masked".

AI apps can list tasks and suggest new ones or changes through the `scheduled_tasks` tool. Its list comes in pages (`limit`, default 50, at most 200; `next_cursor` while `has_more`) with the total and a count per state, and `brief: true` gives one line of facts a task; `action: "get_run"` with a `run_id` returns one run's full summary, output and details. A suggestion shows as **Needs your approval** and never runs (an approved task keeps running unchanged) until you approve it in Settings; agents cannot approve. A finished run can post a macOS notification that says how it ended, never the prompt or the result.

## Agent team budgets and adaptive retry

### Failure-aware team outcome and quorum

`wait_agents` separates **completion** from **success**. `mode="all"` keeps its existing completion meaning (`condition_met=true` once all relevant work is terminal), while additive `success`, `outcome`, and `partial_failure` fields say whether the finished work actually succeeded. `mode="any"` and `mode="majority"` count only successful `completed` work; failed, timed-out, stalled, cancelled, skipped, budget-exhausted, and quality-failed work cannot satisfy a success quorum. For DAG teams, quorum is calculated over task outcomes rather than historical agent attempts, so retries/revisions do not distort the denominator.

Normalized work outcomes are `running`, `completed`, `partial_failure`, `failed`, or `cancelled`. `timed_out` is deliberately separate and means only that the **wait call's deadline** expired while its condition was still possible; an agent whose own status is `timeout` is reported as failed work, not as a waiter timeout. Responses also include successful/failure/pending counts, quorum totals/thresholds, `quorum_possible`, and structured task/agent failure reasons. Existing team `status`, `count`, `terminal_count`, agent rows, and nested `team` fields remain available for compatibility.

`spawn_agents` applies shared team admission thresholds on top of each child agent's own timeout. `max_parallel` remains the concurrency ceiling; `team_timeout_s` bounds how long the scheduler may admit new DAG nodes. Optional `admission_tool_call_budget` and `admission_token_budget` stop new DAG nodes and retries once observed team usage reaches the configured threshold. They are intentionally not hard runtime caps: agents that were already running may finish and push observed usage past the threshold rather than being killed at an unsafe side-effect boundary. Team summaries expose the contract, used/remaining values, overshoot, and whether work is still active at the threshold. The older `max_total_tool_calls` and `max_total_tokens` names remain deprecated aliases for compatibility and have the same admission-only semantics.

`max_team_retries` is a separate shared retry budget. Automatic retries are classified before replay: rate limits, timeouts/stalls, provider overload and transient transport failures may retry; authentication, permission, quota, invalid-model/request and unknown provider failures fail fast. Durable side-effect/checkpoint safety takes precedence over error classification, and every team retry slot is reserved atomically with bounded start spacing so concurrent failures cannot create a retry storm. `admission_token_budget` counts provider-reported usage; an agent whose provider reported nothing is listed as unknown rather than counted as zero.

## Memory and Agent Skills API surface

The native MCP endpoint remains the full Memory and Agent Skills surface. REST/OpenAPI intentionally exposes only the read-oriented compatibility subset: `memory_search`, `memory_get`, `skill_list`, `skill_search`, and name-based `skill_get`. These routes use the same server authentication, permission profile, scoped tool-family authorization, and security-context gate as the rest of the published REST surface.

Memories are stored as Markdown day files under `~/.mac-mcp/memory` (or `MAC_MCP_MEMORY_DIR`) plus a local SQLite search index; the folder, files and index are kept owner-only even for a custom location. Deleting a memory removes it from the Markdown file (and the file itself once a day has no memories left) and from the index, its full-text and vector rows, with SQLite secure-delete and a WAL checkpoint so the text does not linger in the database; this is not a forensic disk wipe. **Settings → Usage → Memory** shows how many memories exist, exports them all as JSON, deletes them all after showing how many will go, and sets an optional retention period (until deleted by default; 90 days to 2 years), which keeps high and critical memories unless you turn that off.

Memory mutation (`memory_add`, `memory_update`, `memory_delete`) and Agent Skill registration/index mutation (`skill_register`, `skill_update_index`) remain **MCP-only**. REST `skill_get` accepts an exact skill name but deliberately does not accept a `SKILL.md` path because MCP path lookup may register an external skill. Public REST responses also omit local-only filesystem/index metadata such as memory file paths, skill roots/directories/absolute resource paths, and index-sync diagnostics.

## Role learning for delegated agents

Mac MCP keeps **workflow lessons** separate from generic factual memory. Delegated agents can opt into a role with `role="coder"`, `role="reviewer"`, or `role="orchestrator"`. At spawn time, only a small top-k set of **approved, relevant** lessons for that role is injected; current task instructions always take priority. Unrelated tasks receive no lesson context.

A worker may emit a compact structured lesson candidate at the end of a run, but candidates are quarantined and **never auto-activate**. `lesson_search` lets the parent review candidates and `lesson_feedback` records `approve`, `success`, `failure`, `disable`, or `enable` outcomes. Repeated failures lower confidence and can disable a lesson; stale low-confidence lessons can be disabled during `lesson_consolidate`. Exact duplicates merge within the same trust domain, while contradictory preferred actions are reported for review instead of silently choosing a winner. Manual candidate creation and consolidation remain available through tool discovery so the compact core tool surface stays small. `lesson_export` returns every stored lesson for review, and `lesson_delete` removes one lesson, a role's lessons, or all lessons after `confirm=true` (deleted text is overwritten on disk). Lessons not updated or used for `privacy.lesson_retention_days` (default 365, `0` keeps them until deleted) are removed automatically and never reach a worker prompt.

Role lessons are stored as structured fields and bounded evidence references in `~/.mac-mcp/role-learning/role-lessons.sqlite3`; raw agent transcripts are not stored in the lesson database. Sticky provenance is enforced: a web-tainted session cannot write or approve trusted lessons, tainted children do not receive trusted lesson context, and untrusted candidates are kept in a separate quarantine namespace so they cannot poison an existing trusted lesson.

## Claude Code subagents

Enable **Claude Code** in **Settings → Subagents** and delegate with `provider=claude`. Mac MCP runs the installed `claude` CLI headless (`--print --output-format stream-json`) and reads its event stream for phase, tool calls, effective model, session id and token usage; `agent_action(action=resume)` continues the same Claude Code session.

- **Models:** the catalog offers the aliases `fable`, `opus`, `sonnet` and `haiku`, which always resolve to the newest model of each family; a full id such as `claude-opus-5-5` is accepted too. Without a model the owner's Claude Code default (`model` in `~/.claude/settings.json`) is used. `reasoning` maps to `--effort` (`low`, `medium`, `high`, `xhigh`, `max`).
- **Access modes:** `read_only` and `workspace_write` run the CLI and everything it starts inside the same macOS Seatbelt boundary as Codex and OpenCode, with a private home and config directory per agent (the owner's transcripts, plugins and hooks are not visible). `read_only` also removes Claude Code's file-writing tools. `full` runs with the owner's normal Claude Code environment.
- **Sign-in:** `full` uses the owner's Claude Code sign-in directly. A sandboxed agent receives only the short-lived access token of that sign-in, never the refresh token, so an agent cannot rotate it and sign the owner out; a token close to expiry is renewed with `claude auth status` first. Set `MAC_MCP_CLAUDE_CODE_OAUTH_TOKEN` to a `claude setup-token` token to use a dedicated long-lived token instead. The token is scrubbed from the agent's own Bash/hook child processes.
- **Tools:** every agent gets only the scoped Mac MCP server (`--strict-mcp-config`), not the owner's other MCP servers or connectors. Tools whose effects outlive the agent or leave Mac MCP's control (`CronCreate`, `CronDelete`, `RemoteTrigger`, `ScheduleWakeup`, `PushNotification`, `SendMessage`, `ListAgents`, `ShareOnboardingGuide`, `DesignSync`, `Workflow`, `EnterWorktree`, `ExitWorktree`) are removed in every mode, so cancel and despawn stop all of an agent's work.
- **Replay safety:** a run that used a state-changing native tool (`Bash`, `Edit`, `Write`, `NotebookEdit`, `Task`, `Skill`, …) is never replayed automatically; read-only tools (`Read`, `Glob`, `Grep`, `WebFetch`, `WebSearch`, …) and Mac MCP's own receipted tools keep automatic retry available. Failures are classified from Claude Code's own result (`api_error_status`), not from tool output.

## Kimi Code and Grok Build subagents (experimental)

Off by default. Install the CLI (`npm install -g @moonshot-ai/kimi-code` or `@xai-official/grok`), sign it in or give it a model, then turn on **Kimi Code** or **Grok Build** in **Settings → Subagents** and delegate with `provider=kimi` or `provider=grok`. They work like the other providers: Mac MCP runs the CLI headless (Kimi `--prompt … --output-format stream-json`, Grok `--single … --output-format streaming-json`) and reads its event stream for phase, tool calls, session id and, for Grok, token usage; `agent_action(action=message)` continues the same session.

- **Models:** Kimi offers the model aliases of the owner's `~/.kimi-code/config.toml` (its `default_model` without a model); Grok offers what `grok models` lists. Both CLIs can use any OpenAI-compatible provider, so a model set up with an API key variable (`api_key_env` in Kimi, `env_key` in Grok; `OPENROUTER_API_KEY` is also read from the Keychain) works without a subscription. Grok takes `reasoning` (`--reasoning-effort`); Kimi takes none.
- **Sign-in:** a spawn is refused with `provider_sign_in_required` when the CLI has no way to reach a model: no `kimi login`/`grok login`, no `KIMI_API_KEY`/`XAI_API_KEY` for the server and no configured model with a key.
- **Private home:** every agent runs with its own `KIMI_CODE_HOME`/`GROK_HOME` under its agent directory. The owner's model settings and sign-in (`credentials/`, `auth.json`) are copied in for the run and removed again when it ends or is cancelled; the owner's own MCP servers are left out and only the scoped Mac MCP server is added. A follow-up runs in its first agent's home, where the session is.
- **Access modes:** `read_only` and `workspace_write` run the CLI and everything it starts inside the same macOS Seatbelt boundary as the other providers. Both CLIs run their tools without asking in this mode (Kimi's prompt mode always does; Grok gets `--permission-mode bypassPermissions`), so the boundary is what limits them: in `read_only` a write is refused by macOS, and Grok also loses its `write` and `search_replace` tools. Grok's scheduler and subagent tools are removed in every mode. `full` runs without a boundary.
- **Usage:** Grok's own report is recorded once per run (Settings → Usage shows it once Grok Build is on); Kimi reports no usage, and missing usage is shown as unavailable, never as zero.
- **Replay safety:** a run that used a native tool that can change something (shell, file writes, any tool not known to only read) is never replayed automatically; reads and Mac MCP's own receipted tools keep automatic retry available.
- **Limits:** only Kimi Code 2.2 and Grok Build 1.0.52 were tested, against a free OpenRouter model; a CLI update that drops an option Mac MCP passes is reported as `provider_incompatible` before any work starts.

## Antigravity, pi, Cline, Kilo Code and Goose subagents

Off by default, like Kimi and Grok: install the CLI, sign it in or give it a model, then turn it on in **Settings → Subagents** (or with its switch in the tour's Connect screen) and delegate with `provider=antigravity|pi|cline|kilo|goose`. A model is `provider/model`, for example `openrouter/nvidia/nemotron-3-super-120b-a12b:free`; `OPENROUTER_API_KEY` is also read from the Keychain. Each one's own event stream gives phase, every tool call (Mac MCP's own named as such, its shell commands and file writes as commands and files in run reports and the menu), the answer, the session id and token usage, which Settings → Usage shows per agent.

| Agent | CLI (tested) | Headless run | Private state per agent | Follow-ups |
|---|---|---|---|---|
| Antigravity | `agy` 1.3.5 | `agy --print … --output-format stream-json` | none: runs on the owner's sign-in | `--conversation <id>` |
| pi | `pi` 1.2.0 (`@earendil-works/pi-coding-agent`) | `pi --print --mode json` | `PI_CODING_AGENT_DIR` (copy of `auth.json`, `models.json`) | `--session <id>` |
| Cline | `cline` 3.0.71 | `cline --json --auto-approve true` | `--config`/`--data-dir` (copy of `providers.json`) | not available headless |
| Kilo Code | `kilo` 7.8.12 (`@kilocode/cli`) | `kilo run --format json --auto` | `XDG_*` dirs | `--session <id>` |
| Goose | `goose` 1.54.0 | `goose run --output-format stream-json` | `GOOSE_PATH_ROOT`, no keyring | `--resume --name <agent>` |

- **Mac MCP's tools:** each gets only the scoped Mac MCP server in its private config, never the owner's own MCP servers. Antigravity's sign-in lives in the owner's Keychain and `~/.gemini`, so it runs with the owner's HOME; its scoped server reaches it as an added workspace folder (`--add-dir`) holding `.agents/mcp_config.json`, and the owner's agy configuration is never changed.
- **Access modes:** pi, Cline, Kilo Code and Goose run inside the same macOS Seatbelt boundary as the other providers in `read_only` and `workspace_write`. Antigravity runs with `access_mode=full` only: agy reads its sign-in with `/usr/bin/security`, which the boundary refuses so that no agent can read the owner's other Keychain secrets; a restricted spawn is refused with that reason.
- **Follow-ups:** Cline 3.0's `--id` opens its interactive chat, which `--json` refuses, so a Cline agent offers no session to continue (`supports_resume: false`).
- **Replay safety:** as for the others, a run that used a native tool that can change something is never replayed automatically; reads and Mac MCP's own tools keep automatic retry available.
- **Tested:** each end to end through an isolated Mac MCP server with its own shell, a file write and a Mac MCP tool, then a follow-up in the same session (Antigravity with Gemini 3.8 Flash, the others with a free OpenRouter model).
